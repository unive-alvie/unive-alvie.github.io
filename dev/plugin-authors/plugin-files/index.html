Plugin Files Reference

Preview

ALVIE is becoming a framework: a small ALVIE/Core that learns and compares models, and plugins that connect it to a platform. A plugin describes its platform in six YAML files and implements a backend that runs inputs on it. This page is the reference for those files and for the spec language that Core builds from them.

Status

ALVIE/Sancus is declared in these files (plugins/sancus/), and learning and comparison use them: the input generator follows the phase rules and the spec’s constraints, the backend contract gives the simulator the programs of the sections, and comparisons see what the attacker view declares. The command line and the tools for plugin authors are still those of ALVIE/Sancus.

Layout

Section titled “Layout”

A plugin is a directory:

Two plugins come with ALVIE: plugins/sancus, for Sancus, and plugins/tiny, Tiny, the reference platform of ALVIE/Core. Tiny is the smallest complete plugin: read its files next to this page.

Every file starts with format: 1, the version of its format. Core checks each file, then checks the files against each other, and reports every error it finds with its file, line and column.

Writing the files

Section titled “Writing the files”

The files are YAML, with three restrictions:

  • No anchors, aliases or tags (&a, *a, !tag): they are not needed, and aliases can make a small file expand into a huge one.
  • No duplicate keys in a mapping.
  • No unquoted yes, no, on, off, y or n. YAML 1.1, which the parser implements, reads them as booleans; YAML 1.2 and most editors read them as strings. Quote them ("on") when you mean the word, and write true or false for a boolean.

In a flow mapping ({ ... }), quote any text that contains a comma: doc: "Starts the timer, which interrupts".

Editor support

Section titled “Editor support”

alvie/code/schemas/ holds a JSON Schema for each file. Editors that understand JSON Schema complete the field names and show errors as you type. With the YAML extension of VS Code, start the file with a comment that points to its schema:

The schemas are generated from the code that reads the files, so the two always agree. They cover each file on its own; the checks across files (for example, that a rule names a declared section) happen only in Core.

alvie-plugin.yaml: the manifest

Section titled “alvie-plugin.yaml: the manifest”
FieldRequiredMeaning
formatyes1
nameyesThe name of the plugin.
versionyesThe version of the plugin.
coreyesThe version of the plugin interface of ALVIE/Core that the plugin targets: "1".
kindyesnative (OCaml, linked with Core) or external (a program that speaks Core’s protocol).
commandexternal onlyThe command that starts the backend, as a list: [python3, backend.py].
descriptionnoA description.
confignoThe configuration parameters of the backend, by name (see below).
variantsnoThe variants of the system, by name, each with an optional doc: for example a baseline such as no-interrupts.
capabilitiesnoWhat the backend can do: restore, clone, parallel.
filesnoThe names of the other files, if they differ from the defaults above.
fixturesnoThe directory of the plugin’s fixtures, relative to the manifest (see Fixtures).

A configuration parameter has a type (string, path, int, bool or enum), and optionally required: true, a default (written as on the command line), a doc, a range: [lowest, highest] for int and the values of an enum. Each parameter is an option of the plugin’s commands, --<name>, checked against its type.

A variant is a version of the system that the backend can run instead, chosen with --variant: Tiny and Sancus have no-interrupts, the baseline whose differences are not caused by interrupts.

sections.yaml: sections and the secret

Section titled “sections.yaml: sections and the secret”

Each section has:

FieldMeaning
roleattacker or victim. The inputs of attacker sections are the low inputs of a comparison.
kindcode (the default), stimulus or opaque; see below.
atomsThe atom class of the section’s inputs: an entry of atoms: in atoms.yaml. Opaque sections have none.
initialtrue for the one section the system starts in.
docA description.

The kinds:

  • code: the section is code. All the runs of a section in one test are prefixes of its longest run: when a test enters the section again, Core replays the code that already ran and chooses new atoms only beyond it.
  • stimulus: each input is a fresh choice, never replayed (for example bus transactions).
  • opaque: the backend supplies the program (for example an existing binary); its only input is Core’s built-in run.

The secret is either { hole: true }, the variant of atoms.yaml marked secret, or { config: <parameter> }, a configuration parameter of the backend. Either form may list the values to compare.

atoms.yaml: atoms and their syntax

Section titled “atoms.yaml: atoms and their syntax”

types: declares the types of arguments, and atoms: the atom classes. Both share one set of names. A type has either one form (syntax and args) or variants, each with its own syntax and args. An atom class is a set of variants: its atoms.

Argument types

Section titled “Argument types”
TypeValues
intA non-negative integer.
{ int: [lowest, highest] }An integer in this range.
symbolA name made of letters, digits, _ and -.
A declared type or atom classIts values.
{ list: <type>, exclude: [...], sep: ";" }One or more values of the type, separated by sep (default ;), without the excluded variants.

Syntax templates

Section titled “Syntax templates”

A template is a format string: "mov {src}, {dst}". Every argument appears exactly once. Spaces in a template are printed as one space; when Core parses, whitespace is optional between any two parts of a template. A type can give a list of templates: all of them parse, and the first is the one that Core prints.

When several variants can read the same text, the first one declared wins. For example &r5 is a register before it is a symbol if the register variant comes first. A template cannot start, directly or through its arguments, with its own type (left recursion): Core reports it.

The secret

Section titled “The secret”

The variant marked secret: { expand: "<template>" } is the hole of the secret. Its syntax (for example ?) parses to the hole, and the secret value replaces it by its expansion, with {value} replaced by the value: with expand: "#{value}" and the secret 1, ? becomes #1.

Attributes

Section titled “Attributes”

Attributes describe atoms for the constraints of specs, for example the registers that an instruction reads. Declare each attribute with the type of its values, and list, for each atom (or variant) that has it, the arguments its values come from:

The values of an attribute in an atom are the values of its type found in the listed arguments. Inside them, a variant that lists the attribute contributes the values of the arguments it lists, and a variant that does not list it contributes those of all its arguments. An atom that does not list an attribute has no value for it, and nested atoms (as in a list of atoms) contribute their own values. With the declarations above, mov r5, r6 reads r5 and writes r6.

observations.yaml: what the backend observes

Section titled “observations.yaml: what the backend observes”

Each observation has a kind and typed fields. A kind is declared as {} (no fields), as the name of a record type (its fields), or with fields:. Field types are int, bool, word (an integer from 0 to 65535), { int: [lowest, highest] }, or a declared enumeration (enum:) or record type (fields:).

phases.yaml and view.yaml: rules

Section titled “phases.yaml and view.yaml: rules”

Both files are lists of rules, and the first rule that matches an observation applies. A rule matches with up to three keys:

KeyMatches
matchA kind or a list of kinds (all kinds if absent). It is called match, not on, because YAML 1.1 reads on as a boolean.
inPhase rules only: the current section, or a list of sections.
whenValues of fields, all of which must hold: { mode: PM }. A field of a record field is written with a dot: time.mode.

Phase rules

Section titled “Phase rules”

do lists the actions, applied in order:

ActionEffect
restartThe test starts afresh, in the initial section, as if nothing had run: the platform rebooted, and the programs of the sections can be new.
resetEvery section starts again, with the same programs. The position saved by the last interrupt stays.
{ enter: S }S starts again (a new run) and becomes current.
{ switch: S }S becomes current where it was (its run goes on).
{ interrupt: S }The position of the current section is saved (in place of the one saved before), and S is entered.
resumeThe section interrupted last becomes current again, at the position where it was interrupted. That position stays saved, so a second resume returns to it again. Nested interrupts are not supported yet.
{ stop: finished }, { stop: invalid }The test stops.

do: [] changes nothing.

The saved position stays after a resume and after a reset because some platforms allow it: on Sancus, an attacker can execute reti twice and re-enter the enclave where the timer last interrupted it (attack B3). Whether a resume happens is for the platform’s observations to say; the phase rules only follow them.

Attacker view

Section titled “Attacker view”
showThe attacker sees
hiddenNothing: the observation is silent in comparisons.
tagOnly the kind.
{ fields: [...] }The kind and these fields.
distinctThe observation, which is never equal to another one, so it is always reported.
allEverything.

Some observations stand for several events, for example an instruction that ran and an interrupt that was handled. A parts: rule splits them; each part is then seen by the show rules (parts are not split again):

A part is an observation of the kind as, with a record field of the observation (field: time), its own fields (field: self), or no fields at all (no field). Its input is the input of the step, or, with input: interrupt, the built-in interrupt, which the attacker controls: the two runs of a witness must have their interrupts at the same places.

What comparisons take from these files

Section titled “What comparisons take from these files”

Core compares models only through these files, with nothing written for a platform:

  • what the attacker sees, and which outputs are silent, from view.yaml (the comparison sees only what the attacker sees: on Sancus, not the cycle count k);
  • where a run ends: the outputs whose phase rule stops (stop: finished) or restarts the test;
  • which inputs the attacker chooses (the low inputs): the atoms of attacker sections, and interrupts;
  • the victim’s code of a run: the atoms of victim sections until it is interrupted or the test goes to another section; two runs of a witness must run the same victim code, up to the secret (its values in the atoms are ignored).

How Core generates inputs

Section titled “How Core generates inputs”

Learning asks Core, at every step of a test, which inputs the spec allows next. Core follows the test through its sections with the phase rules, and offers the atoms that the current section’s body accepts next, in the order atoms.yaml declares them.

Sections of kind code follow the prefix rule. Running a section again runs the same code from its start, so all the runs of a section in one test are prefixes of its longest run, its program. When a run is at a position that the program already has, the only option is the program’s atom there; new atoms are chosen only beyond its end. A run starts when the section is entered (enter, or an interrupt into it); switch and resume continue a run. A resume into the middle of a run therefore replays the program from that position.

Sections of kind stimulus choose afresh at every input, and an opaque section offers only the input run.

Checking a plugin

Section titled “Checking a plugin”

alvie plugin check DIR reads the files of the plugin in DIR, checks them and their references to each other, and prints every problem with its place, or a summary of the plugin; without DIR it checks the plugin that alvie is built with. alvie plugin schemas OUT writes the JSON Schemas of the files, and those of the values of the plugin’s atoms and observations, to OUT.

The configuration parameters of the manifest are the options of the backend on the command line: alvie learn --commit bf89c0b sets the parameter commit.

Two more checks need the backend, and run with the plugin’s commands (alvie tiny ..., alvie sancus ..., or the alvie-NAME of a new plugin):

  • conformance runs random tests of a spec and checks that the backend keeps the contract of Core;
  • fixtures learns and compares the fixtures, and checks their verdicts.

The Plugin Author Guide explains both.

Fixtures

Section titled “Fixtures”

A fixture is a spec with the verdict of noninterference that the plugin must give on it: a planted leak that must be found, a safe spec that must give no witness, or a known attack. fixtures learns a model of the spec for each of the two values of the secret (and of the baseline variant, if there is one), compares them as compare does, and checks the verdict. Each fixture is a YAML file in the directory that the manifest’s fixtures: names:

The values in config: override the options of the command line, which give the others (Sancus needs --sancus and --tmpdir); a parameter left out has its default. The fixtures of Tiny are in plugins/tiny/fixtures, and those of Sancus, which take a few minutes each, in plugins/sancus/fixtures.

Checks across files

Section titled “Checks across files”

After reading each file, Core checks that:

  • every section names an atom class of atoms.yaml;
  • the secret is a variant marked secret, or a parameter of the manifest;
  • every kind and section in a rule is declared;
  • the fields in when: and show: exist in every kind the rule matches (a rule without match: needs at least one kind with the field), and the values in when: have the field’s type.

Specs

Section titled “Specs”

A spec gives one body per section. It may be split across files, as ALVIE/Sancus splits the victim (.etdl) and the attacker (.atdl). Every section that is not opaque has exactly one body.

A body is a regular expression over the atoms of its section’s class:

| is a choice, ; a sequence, * any number of repetitions, and eps the empty sequence. ; binds tighter than |: write (nop | eps); call for “maybe nop, then call”. Whitespace is allowed anywhere between the parts, and a comment runs from // to the end of the line.

Constraints

Section titled “Constraints”

A constraint block states what must hold over a whole test, across sections:

ConstraintHolds when
disjoint(A, B)No value is in both sets.
subset(A, {v, ...})Every value of A is listed. The second set must be a list: an attribute can still grow.

A set is attribute(section), the values of the attribute in all the atoms that the section has run in the test, or a list of values of the attribute’s type, such as {r12, r13}. Core offers a new atom only if every constraint still holds with it, and if the section can still reach the end of its body with atoms that keep the constraints, so that a test never runs into a dead end of its own section. Atoms that the prefix rule replays are always offered: they ran before, so their values are already counted.

threads { ... }; and step <unit>; are reserved for later versions: Core recognises them and reports that they are not supported yet.

Values

Section titled “Values”

Every atom and observation is a value: an integer, a boolean, a symbol, a list, a node (a variant or a record: its tag and its fields, in the order of the declaration), or the hole of the secret. In JSON, the form the external protocol will use, a node is an object with a single member, its tag: mov r5, r6 is {"inst": {"i": {"mov": {"src": {"reg": {"r": {"reg": {"i": 5}}}}, "dst": {"reg": {"r": {"reg": {"i": 6}}}}}}}}, and the hole is {"?": "secret"}.
