Plugin Author Guide

Preview New

A plugin connects ALVIE/Core to a platform: its files declare what tests are made of and what the attacker sees, and its backend runs the tests. Core does the rest: it generates the inputs that a spec allows, learns models, and compares them. This guide takes you from nothing to a plugin that learns, checks and finds a leak. Read the Tiny tutorial first: it uses a finished plugin.

A plugin is native, with a backend in OCaml linked with Core, or external, with a backend that is a program in any language speaking the protocol of Core. The Python SDK makes external plugins easy to write; native ones are faster (see Cost).

2. Describe the platform

Section titled “2. Describe the platform”

The Plugin Files Reference documents each file; Tiny (plugins/tiny) and Sancus (plugins/sancus) are examples. In the order that usually works:

  1. sections.yaml: the parts of a test, who writes them (attacker or victim) and which atoms each runs. Most platforms have the attacker before and after the victim (prepare and cleanup), and an interrupt handler if the attacker can interrupt it.
  2. atoms.yaml: the instructions or actions of each section, with their syntax, as a spec writes them. Mark the variant that is the secret.
  3. observations.yaml: what the backend reports after each input. Report what an attacker could measure, and anything Core needs to follow the test (for example that the victim was entered).
  4. phases.yaml: how each observation moves the test between sections.
  5. view.yaml: what the attacker sees of each observation. Hide what only the platform knows.
  6. alvie-plugin.yaml: the configuration of the backend (each parameter becomes an option, --name), the variants (such as a baseline without interrupts) and the capabilities.

alvie plugin check plugins/my-chip reports every problem with its file, line and column; editors with JSON Schema support complete the fields as you type.

3. Write the backend

Section titled “3. Write the backend”

The backend implements the contract between Core and a platform: Alvie_backend.Backend.S (lib/core/backend/backend.ml) for a native plugin, the class Backend of the SDK for one in Python (its methods have the same names, and the protocol has the same messages):

FunctionDoes
preStarts a test from the initial state of the platform.
stepRuns one input and returns its observations (values of observations.yaml) and its bookkeeping.
restoreA dry step: Core already knows the observations; update the state as if the step ran.
cloneAn independent copy, for learning in parallel and for the exhaustive oracle, which explores the branches of a test from copies.
postEnds a test.

For each step, Core gives the input’s section, its position in the section’s run, its atom, and the programs of all the sections (the code each runs in this test): a backend that compiles code, as Sancus does, generates it from them. Bookkeeping is what the backend needs to continue a test that Core should not compare (Sancus: the code still to analyse); Core stores it and gives it back to restore. The template and Tiny have none.

In Python, step gets a Step (section, position, atom, programs) and returns the list of observations; read atoms with tag and get (get(step.atom, "v", "num")), and make observations with the generated constructors (obs.Exit(time=3)). Write logs with log(): standard output carries only the protocol.

A native plugin is the module Native of the backend (Alvie_backend.Native.S): the plugin files, embedded in the program by the rule in dune, the backend, and make, which builds a backend from the values of the configuration parameters and the variant.

4. Check the backend: conformance

Section titled “4. Check the backend: conformance”

conformance runs random legal tests of a spec and checks that the backend keeps the contract:

CheckA failure usually means
observationsThe backend returns a kind or a field that observations.yaml does not declare, or a kind that no phase rule matches (add one with do: [] if it changes nothing).
phasesThe backend rejects an input that the spec allows: the phase rules do not follow the platform, or the backend does not support an atom.
determinismThe backend depends on something other than the inputs: time, randomness, files of an earlier run. Learning needs a deterministic system.
resetpre does not reset everything, or a cache of the backend is keyed by less than it depends on.
prefixesThe same as reset, from another angle: state kept between tests.
restorerestore does not leave the state that step would.
cloneclone shares state with the original.

restore and clone are checked only if the manifest declares the capability. A failure prints the first test that shows it; replay it with exec. For an external plugin, conformance also checks the protocol: an answer that is not one, or a plugin that crashes or hangs, stops it with a message and the end of the plugin’s log (see Errors). Use --tests, --length and --seed for more or other tests, and run conformance on several specs: it only explores what a spec allows.

5. Check the verdicts: fixtures

Section titled “5. Check the verdicts: fixtures”

A backend can keep the contract and still model the platform wrongly. Fixtures pin down what the plugin must find: write a spec for a leak you know of, one that is safe, and the known attacks on your platform, each with its verdict (see Fixtures).

A failing fixture keeps its models and witness graph in --out.

6. Use the plugin

Section titled “6. Use the plugin”

The commands of alvie-my-chip are those of the Tiny tutorial: learn models of your specs, compare them, and read the witnesses. To add the plugin to alvie itself, as alvie my-chip ..., add a line to bin/alvie.ml and the library to bin/dune, as for tiny.

Limits of this release

Section titled “Limits of this release”
  • The comparison lists, for each counterexample, every path of each model that matches it. A spec whose attacker loops ((timer 1 | nop)* before the call) has many, and comparing can take very long: let the attacker choose once, as the fixtures of Tiny do.
  • Errors of the command line itself (an unknown option, a value of the wrong type) are reported by the parser with exit status 1; the other mistakes in a command or its files exit with 2.
